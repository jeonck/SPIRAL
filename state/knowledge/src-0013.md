## Summary

arXiv 2606.31159 (submitted 30 Jun 2026; cs.SE + cs.CR + cs.LG), accepted at the 42nd
International Conference on Software Maintenance and Evolution (ICSME 2026), Research
Track. Authors: Mohammed Latif Siddiq, Md. Nafiu Rahman, Joanna C. S. Santos. No
overlap with src-0001's authors (Mezzi, Massacci, Tuma) or with any other team in this
knowledge base.

Why it was added (cycle 15, T1 targeting `consistency-calibration-as-failure-mode`):
this issue has been stuck at score 2 since cycle 3 for one reason only — BOTH of its
candidate_resolutions cite src-0001 and nothing else, and single-source support is a 2
by rubric. This is the first source in the base other than src-0001 that measures
**confidence calibration with ECE and Brier score on a security task**. It is therefore
the direct unblocker for that issue, subject to the scope gap recorded below.

Its substantive contribution beyond "a second ECE measurement exists" is that it
independently reproduces src-0001's most counter-intuitive finding — that an
intervention intended to improve behaviour can make calibration *worse* — in a
different domain, with a different mechanism. src-0001 found fine-tuning raised
gpt4o CVE-generation ECE from 0.15 to 0.91. This paper finds that moving from a
controlled benchmark to a realistic repository-level setting raises ECE across every
model tested, and that architectural gating improves calibration on the controlled
benchmark while degrading it in the realistic one.

## Key claims

1. **Overconfidence is prevalent and ECE/Brier were measured per model.** On the SALLM
   benchmark with verbalized confidence: GPT-4o-mini ECE in [0.456, 0.481] (Brier
   0.37–0.39); Qwen3-Coder-Next ECE in [0.408, 0.421] (Brier 0.36–0.38);
   Gemini-2.0-Flash comparatively better at ECE in [0.247, 0.263] (Brier 0.26). Ranges
   are across six temperature settings (0.0–1.0). This is an independent
   security-domain measurement of the same two metrics src-0001 reports for gpt4o.
2. **Calibration degrades sharply when the setting becomes realistic rather than
   controlled — the same direction-of-surprise as src-0001's fine-tuning result.**
   "Repository-level generation has higher calibration error across all models":
   GPT-4o-mini average ECE rises from 0.411 on SALLM to 0.697 on repository tasks
   (ΔECE = +0.286), and Gemini-2.0-Flash from 0.161 to 0.721 (ΔECE = +0.560). The
   authors state that although architectural gating "improves calibration on controlled
   benchmarks, calibration deteriorates in realistic repository-level settings,
   increasing the risk of high-confidence vulnerable outputs."
3. **Miscalibration is quantified as an operational risk, not just a metric.** The paper
   defines a False Trust (FT) rate — the share of high-confidence predictions that are
   wrong, FT(τ) = |{i : p_i ≥ τ ∧ y_i = 0}| / N at τ = 0.8 — and reports GPT-4o-mini
   33.9%, Gemini-2.0-Flash 17.5%, Qwen3-Coder-Next 38.3%. It also reports that
   functional calibration is consistently *worse* than security calibration
   (ΔECE = ECE_s − ECE_f negative for every model: −0.15 to −0.16 GPT-4o-mini,
   −0.26 to −0.27 Gemini, −0.52 to −0.53 Qwen), i.e. calibration is itself
   task-dependent within a single study — which bears on
   `task-dependent-reliability-framing` as well.

## Relevant quotes

Abstract, verbatim, from https://arxiv.org/abs/2606.31159:

> "Large Language Models (LLMs) are rapidly transforming software development, yet their
> use in security-critical contexts raises a key question: do models know when their
> generated code is insecure? This property, known as calibration, measures whether a
> model's confidence aligns with the true correctness of its outputs. We present the
> first large-scale empirical study of security calibration in LLM-generated code. We
> evaluate GPT-4o-mini, Gemini-2.0-Flash, and Qwen3-Coder-Next across multiple
> temperature settings on two complementary benchmarks: self-contained security tasks
> and multi-language repository-level contexts. Our results suggest that overconfidence
> is prevalent across the evaluated LLMs. Functional calibration is consistently worse
> than security calibration, suggesting that models estimate security outcomes more
> reliably than functional correctness, potentially because functional correctness
> depends on complex execution behavior. We also examine whether calibration-guided
> automated repair can help remediate vulnerabilities in LLM-generated code, finding
> only limited improvements while frequently introducing functional regressions.
> Moreover, we study different mitigation strategies for reducing False Trust, where
> models assign high confidence to vulnerable code. The results show that although
> architectural gating improves calibration on controlled benchmarks, calibration
> deteriorates in realistic repository-level settings, increasing the risk of
> high-confidence vulnerable outputs."

## Limitations of this source

- **SCOPE GAP — THIS IS NOT CTI, AND MUST NOT BE CITED AS IF IT WERE.** The task is
  *generating code* and self-assessing whether that code is secure. It is not IOC
  extraction, TTP mapping, threat-actor attribution, or threat-report drafting. It
  qualifies as evidence for `consistency-calibration-as-failure-mode` under the
  explicit standard that a calibration measurement on security tasks generally is worth
  admitting with the gap recorded — the same standard under which src-0008 (JavaScript
  code obfuscation) sits in this base. Any claim built on it must say "on security code
  tasks", never "on CTI".
- **Different models from src-0001, which cuts both ways.** GPT-4o-mini,
  Gemini-2.0-Flash and Qwen3-Coder-Next do not overlap with src-0001's gpt4o /
  gemini-1.5-pro-latest / mistral-large-2, nor with src-0002's or src-0005's lists. It
  therefore does NOT answer open_question (ii) — it does not test whether src-0001's
  finding replicates on the specific models shown to struggle with ATT&CK mapping. It
  establishes that the phenomenon is not confined to one model family, which is weaker
  but real.
- **AN INTERNAL NUMBER DISCREPANCY, RECORDED RATHER THAN RESOLVED.** The False Trust
  section gives GPT-4o-mini FT = 33.9%, while the repository-comparison section gives
  GPT-4o-mini FT rising "from 16.9% to 83.2%". 33.9% is neither of those and is not
  their mean. The most likely reading is that the three headline FT rates aggregate
  across benchmarks or temperatures while 16.9%/83.2% are per-benchmark, but the paper
  text pulled here does not state this. **Do not quote 33.9% and 16.9% in the same
  breath without resolving which aggregation each uses**; a future cycle should pull
  the FT table itself.
- **Calibration is measured on VERBALIZED confidence** (the model stating a confidence
  number), which is the same modality as src-0001's, so the two are methodologically
  comparable — but verbalized confidence is known to behave differently from
  token-probability-derived confidence, and no result here transfers automatically to
  logit-based uncertainty.
- Retrieved by automated fetch of the arXiv `/abs` page (abstract, authorship, venue)
  and the `/html/v1` page (numbers). The abstract is verbatim-confirmed. The numeric
  values were returned as quoted fragments rather than as a full pulled table; per the
  standing whole-table rule, **the ECE/Brier/FT tables have NOT yet been pulled in full
  and a future G2 on this source should do exactly that.** Treat the numbers as
  single-pass at present.

### (iv) THE ADJUDICATION — the impeached bullet fails on a SECOND limb → `ctr-0027`

The bullet's clause *"which is the same modality as src-0001's, so the two are methodologically
comparable"* is **false**. **src-0001 does not use verbalized confidence; it derives confidence
from token log probabilities.** Verbatim, `arxiv.org/html/2503.23175v2` §5 *Evaluation Metrics*:

> "We implement calibration analysis by extracting the log probabilities that the LLM assigns to
> the tokens composing the generated response. Considering that the response is in the JSON
> format, and each field of the JSON file corresponds to a different entity, we isolate the
> tokens and the probabilities of each section of the JSON file corresponding to a specific
> entity, multiply the token probabilities of that JSON file section, and derive the overall
> confidence for each entity."

**Consequence, and it is good news.** This file's **Token Probability** block, *not* its
Verbalized block, is the modality-matched counterpart to src-0001. The base gains its first
**modality-valid** cross-study calibration comparison on security tasks. Matched: src-0001
(gpt4o, CTI extraction/generation, token-probability) ECE 0.13–0.47 zero-shot rising to 0.91
fine-tuned, against src-0013 (GPT-4o-mini, Gemini-2.0-Flash, security code generation,
token-probability) ECE 0.79–0.81 flat. **Direction corroborates; magnitudes diverge sharply —
and that divergence must NOT be read as a conflict, because the tasks differ.**
