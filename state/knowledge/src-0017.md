## Summary

The released code-and-data repository accompanying src-0007 (CyberThreat-Eval, arXiv
2603.09452). Added at cycle 21 by a T3 investigating `ioc-extraction-reliability`, under
`prompts/t3_investigate.md` step 2, which permits a T3 to add sources against the same
`max_new_sources` budget as a T1.

Why it was added: contradiction `ctr-0001` has been open since cycle 9 and its stated
primary resolution path is "recover recall/F1 from src-0007's released code (GitHub /
HuggingFace per its abstract)". src-0007 reports **precision only** for IoC extraction —
0.8240 (GPT-4o), 0.8503 (o3-mini), 0.8846 (GPT-4o FT), 0.6944 (GPT-4o-mini FT) — with no
recall and no F1 anywhere in the paper, which is exactly the axis on which src-0003's
legacy baselines were weakest. This repository is the artefact that route depends on.

The repository URL was taken from the paper's own HTML, not from a search summary. That
matters: a web search returned `github.com/secintelligence/CyberThreat-Eval` as the repo,
which **404s**. The paper's own sentence gives the correct pair.

**Outcome, stated plainly: the recall NUMBER for src-0007's four models could not be
recovered, because the paper's model outputs are not in the release. But the release
answers the question behind the number, and answers it more decisively than a number
would have.** The evaluator that produced src-0007's published precision figure computes
recall in the same function and prints it on the very next line. The omission is a
reporting decision, not a limitation of the measurement apparatus.

## Key claims

1. **The released IoC evaluator computes recall by default and prints it immediately
   after precision.** `stage3_ti_drafting/ioc/eval/eval_ioc.py` accumulates
   `total_true_positives`, `total_false_positives` and `total_false_negatives`, then
   computes `precision = total_true_positives / (total_true_positives +
   total_false_positives)` and `recall = total_true_positives / (total_true_positives +
   total_false_negatives)`, emitting both via `print(f"Overall Precision: {precision:.4f}")`
   and `print(f"Overall Recall: {recall:.4f}")`. There is no flag or code path that
   produces precision without recall. **The paper reports the first line of that output
   and not the second.**
2. **The IoC sub-README documents recall as a first-class metric of the benchmark**, so
   this is the benchmark's own design, not an incidental capability of one script:
   "The evaluation uses micro-averaged precision and recall metrics to measure extraction
   accuracy"; "**Recall**: `TP / (TP + FN)` - Measures the completeness of extraction";
   and it interprets the possible outcomes explicitly, including "**High Precision, Low
   Recall**: Your system is accurate but misses many IOCs".
3. **The recall figure cannot be recomputed from this release, because the paper's
   per-model prediction outputs are not published.** The `stage3_ti_drafting/ioc/`
   directory contains `data`, `eval`, `example` and `README.md`; the only prediction file
   named anywhere is `example/prediction/manual_ioc_predictions.json`, a manual example
   used in the quick-start command. No GPT-4o, o3-mini or fine-tuned model output file is
   present. Reproducing recall would require re-running the four models against the
   released ground truth — beyond what a source fetch can establish.
4. **The README flags a recall pitfall that is a plausible — but unconfirmed — motive for
   the omission:** "Recall is calculated against **all** IOCs in the ground truth CSV,
   even if you only predict for a subset of sources", restated as "**Recall Calculation**:
   Recall includes all sources in the ground truth file." Under partial-coverage
   prediction this depresses recall by construction. **The paper never says this is why
   recall was withheld, and no cycle should record that it does.**
5. **F1 is absent from the artefact as well as from the paper** — no occurrence of "F1",
   "f1" or "f_1" in the top-level README, the IoC sub-README or the evaluator. So the
   like-for-like F1 comparison with src-0003's 97.6% is not available from this release by
   any route, even in principle, without re-running the models.
6. **Venue information not present in the arXiv record:** the repository describes itself
   as "[TMLR '25] This repo is the dataset of the TMLR paper CyberThreat-Eval: Can Large
   Language Models Automate Real-World Threat Research?" The arXiv submission is dated
   March 2026 while the tag reads TMLR '25. **The discrepancy is recorded as printed and
   not resolved here**; src-0007's provenance notes should not be updated to assert a
   venue on the strength of a repository badge alone.

## Limitations of this source

- **NOT INDEPENDENT OF src-0007.** Same authors, same artefact, same measurement. It is
  corroborating *material* about src-0007, not a second measurement, and **must never be
  counted as the second of the "≥2 independent sources" a strong claim requires**. Where
  this file and src-0007 are cited together, that is one source's worth of independence.
- **THE README'S EXAMPLE FIGURES ARE NOT RESULTS.** The IoC sub-README displays
  "Overall Precision: 0.8000" and "Overall Recall: 0.6667" as illustrative output of the
  quick-start command run against the manual example predictions. **These are toy numbers
  from a worked example and have no relationship to the paper's measurements. They must
  not be cited as src-0007's missing recall, or as any measurement at all.** This is the
  single most likely misreading of this source and it is recorded first among its risks.
- **Read through rendered GitHub pages and raw file fetches, not by executing anything.**
  The evaluator's logic is transcribed from source; no code was run, so claim 1 is a claim
  about what the script *would* emit, established by reading it. The `test()` function body
  was returned only in part by the fetch — the metric computation and output lines are
  verbatim, the surrounding matching loop is not fully transcribed.
- **The matching rule is loose and its effect on both metrics is uncharacterised.** The
  comments show substring matching in both directions (`pred.lower() in ground truth or
  ground truth in pred`) alongside exact match. A substring-permissive matcher inflates
  true positives relative to strict equality, which affects precision and recall together.
  No cycle should treat src-0007's 0.8240 as a strict-match figure without checking this
  further.
- **Whether the ground truth is exhaustive per article is NOT stated.** The README defines
  the CSV format but never says the listed IOCs are every IOC in the source article. Recall
  against a non-exhaustive ground truth is not comparable to recall against src-0003's
  PRISM, which is described as fully manually validated. **This is an unresolved obstacle
  to the like-for-like comparison `ctr-0001` needs, and it is independent of the missing
  number.**
- **The HuggingFace dataset (`huggingface.co/datasets/xse/CyberThreat-Eval`) was not
  fetched** this cycle. If model outputs exist anywhere in the release, that is where they
  would be, and it is the obvious next step for any cycle continuing this route.
- **No commit hash, tag or access-time snapshot was recorded**, so the file listings and
  code above are as of 2026-07-30 on the default branch and could change.

### What FAILED re-verification — see contradiction `ctr-0004`

The bullet under "Limitations of this source" reading "The comments show substring
matching in both directions ... A substring-permissive matcher inflates true positives
relative to strict equality" was **hedged correctly here** (it says *the comments*, and
it flags the untranscribed loop) but was **hardened elsewhere** into an assertion about
the evaluator's behaviour: this issue's cycle-21 `open_question` says the evaluator
"matches predicted IoCs to ground truth with a SUBSTRING rule in both directions", and
three `scores.json` rationales (cycles 22 and 26) say src-0017 "shows src-0007's
released IoC evaluator matches by two-directional SUBSTRING CONTAINMENT". **That is
wrong.** The executing code, verbatim:

> ```
> # For prediction, if pred.lower() in ground truth
> true_positives = sum(
>     any(pred.lower() in gt.lower() for gt in gt_set)
>     for pred in pred_list
> )
>
> false_positives = len(pred_list) - true_positives
>
> # If for prediction, no pred.lower() in ground truth
> false_negatives = sum(
>     not any(pred.lower() in gt.lower() for pred in pred_list)
>     for gt in gt_set
> )
> ```

The two-directional block (`(pred.lower() in gt.lower()) or (gt.lower() in pred.lower())`)
and the exact-match block are **each enclosed in a triple-quoted string literal** and
never execute. The comments cycle 21 quoted are the headers standing above that dead
code. The sub-README states the live rule in prose, verbatim:

> "A prediction is considered a **True Positive (TP)** if `pred.lower() in gt.lower()`
> for any ground truth IOC from the same source"

**Why the direction matters.** The bias is *asymmetric*, and every downstream use in
this base assumed a single sign:

- **Lenient** — a short or fragmentary prediction that is a substring of a longer
  ground-truth entry scores TP.
- **Strict** — a prediction that *contains* the ground-truth IoC plus surrounding text
  scores a FALSE POSITIVE. That is the characteristic failure mode of a free-form LLM
  extractor, and it is exactly the case the dead two-directional block would have
  scored TP.

So "inflates true positives relative to strict equality" is half the story: relative to
strict equality this matcher inflates on one axis and **deflates on the other**.

### Two further properties of the live code — observation only, supporting no candidate

- Ground truth is built as a **set** per source (`{item.lower() for item in
  cleaned_items}`) while predictions are kept as a **list**, so duplicate correct
  predictions each count as a separate true positive while false negatives are counted
  over the deduplicated ground-truth set.
- Both sides pass through the same normalisation chain, verbatim
  `item.replace("[", "").replace("]", "").replace("hxxp", "http").replace("hxxps", "https").replace("[.]", "[]").split(" - ")[0].strip()`,
  then `.lower()`. Within it the `"[.]"` → `"[]"` step is **unreachable**: both bracket
  characters have already been removed by the two preceding replaces.

simultaneously scored a **false negative**. One answer at the wrong granularity is
penalised twice.

### 2. The documentation describes a rule the code does not run — and here the live code contradicts its own docstring

`compute_raw_precision_recall`'s docstring, verbatim:

> If a TTP's description does not match the expected mapping, issue a warning and do NOT
> add this TTP to the final validated TTPs. (Such TTPs will be treated as false positives.)

`stage3_ti_drafting/ttp/README.md`, verbatim: "**Filtering**: Only TTPs with matching
descriptions are included", and for a worked mismatch example, "Result: **Rejected**
(counted as false positive)".

**The executing `else` branch does the opposite.** It prints
`Warning: Description mismatch for {ttp_id}`, then runs `corrected_details = ttp_mapping[ttp_id]`

with the canonical one and **keeping** the entry.

Unlike `ctr-0004` there is no dead string literal here. The live code simply contradicts the
docstring directly above it.

**Operative consequence: the description check is inert for scoring.** A predicted technique
ID counts on the sole condition that the ID appears in the mapping file, whatever the model
wrote about it. The scorer measures **ID selection only**. Only IDs *absent* from the mapping
are penalised, through `missing_in_mapping_count`, which is added to `fp`.

### 3. Leniency in the opposite direction — recorded so the bias is not assumed to run one way

A `json5` parse failure on a string result executes `continue`, and the whole per-article
block sits inside a bare `except Exception` printing `Error processing article`. An article
whose model output is malformed is therefore **dropped entirely**: no false negatives for its
ground truth, no false positives, and it silently leaves the micro-average. Malformed output
is not penalised.

So the docstring-contradicts-code finding is **replicated**, and it is **not** a second instance
of the `ctr-0004` dead-string-literal artefact — the live code contradicts the docstring sitting
above it in the same function.

### The addition: `TTP_Mapping.csv`'s schema, and the discarded parent column

The head of `data/TTP_Mapping.csv` was read verbatim under an **explicit instruction to make no
claim about the whole file** (1,083,078 bytes; it truncates, and cycle 31 retracted two readings
that were truncation artefacts). Header row, verbatim:

```
,TechniqueID,name,longdescription,is sub-technique,sub-technique of,description,tactics
```

0-based naive comma split: field 1 = `TechniqueID`, field 2 = `name`. This **confirms** that
`load_ttp_mapping`'s `fields[1]`/`fields[2]` select the intended columns — an inference cycle 31
made without having checked the column order.

**But field 5 is `sub-technique of`, and it carries the parent ID.** Verified on real data rows:
`T1548` appears with `is sub-technique` = `FALSE` and an empty parent field, while `T1548.001`,
`T1548.002`, `T1548.003`, `T1548.004` and `T1548.005` each appear with `is sub-technique` = `TRUE`
and `sub-technique of` = `T1548`. (Note `.005`, which cycle 31 did not quote.)

`load_ttp_mapping` reads **only** `fields[1]` and `fields[2]` and **discards field 5**.

> **The parent-child relation needed to award parent-level credit for a sub-technique prediction
> is present in the scorer's own mapping file and thrown away by the loader.**

The correct statement of the finding is therefore not that the scorer *omits* partial credit but
that it **discards the data that would enable it** — and both legs of the double-penalty scenario
are demonstrably reachable, since a parent ID and its sub-technique IDs are simultaneously
admissible keys in the same mapping.
