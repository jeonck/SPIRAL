## Summary

Vendor technical report with data, published by Snyk on 29 June 2026, authored by Liran
Tal. It reports VulnBench JS 1.0, a controlled repeatability study of LLM security
review: 10 JavaScript fixture projects with 44 Snyk Code reference findings, run under 6
configurations, **each task run five times** — "10 tasks x 6 configurations x 5
repetitions = 300 runs" — holding code, prompt and harness identical across repetitions.

Why it was added (cycle 15, T1 targeting `consistency-calibration-as-failure-mode`):
this is the **only** source found this cycle that measures the same axis src-0001
measures by the same method — repeating an *identical* query N times and quantifying how
much the output moves. src-0001 used 10 re-prompts per input and reported bootstrapped CI
widths; VulnBench uses 5 identical repetitions per task and reports how many findings
recur across them. src-0014 (PromptAudit) varies the prompt strategy and is therefore a
different axis; this one is the direct methodological analogue.

Its finding is a sharp, quantified split that maps onto the extraction-vs-generation
divide src-0001 found and that `task-dependent-reliability-framing` is about: findings
that correspond to a known ground-truth reference are highly stable across repetitions,
while findings the model volunteers beyond the reference set are mostly one-off noise.

## Key claims

1. **Repeatability splits sharply by whether the finding is grounded in the reference
   set.** "134 of 158 unique reference-matched findings appeared in all five repetitions"
   (84.8% fully stable), whereas "80 of 161 unique-unmatched findings appeared in only
   one of five identical repetitions, while only 22 appeared in all five." So roughly
   half of the model's extra, unmatched findings are single-run artefacts, and only about
   14% of them are fully reproducible.
2. **The instability is not attributable to prompt or input variation, because there was
   none.** All five repetitions per configuration used the same code, prompt and harness;
   the variance is intrinsic to model sampling. This is an independent confirmation, on a
   security task and outside academia, of the phenomenon src-0001 quantified with
   bootstrapped CIs — that identical CTI/security queries do not yield identical answers.
3. **Design and scale, for anyone citing the numbers:** 300 runs total; benchmark is "10
   JavaScript fixture projects with 44 Snyk Code reference findings", each fixture "a
   small Express-based application, ranging from compact single-file snippets to a larger
   todo app"; six configurations comprising Snyk Code SAST as baseline plus Claude Opus
   4.6 (Medium and High), Claude Opus 4.7 (Max), and Claude Sonnet 4.6 (Medium and High).

## Limitations of this source

- **VENDOR SELF-INTEREST IS DIRECT AND STRUCTURAL, NOT INCIDENTAL.** Snyk sells a static
  analysis product, and Snyk Code SAST is the *baseline* the LLM configurations are
  measured against. The study's framing — that LLM security review produces large volumes
  of unrepeatable extra findings — is commercially favourable to the publisher. This does
  not make the repetition counts wrong (they are mechanically checkable in principle and
  the methodology is stated plainly), but it is a stronger conflict of interest than
  src-0005's CrowdStrike/Meta affiliation or src-0007's Microsoft affiliation, both of
  which are already flagged in this base. **Do not use this source alone to support a
  claim that LLM security review is unreliable.**
- **Only one model FAMILY is tested.** Every non-baseline configuration is an Anthropic
  Claude model (Opus 4.6, Opus 4.7, Sonnet 4.6). There is no OpenAI, Google, Mistral or
  open-weight comparison, so nothing here separates a Claude-specific sampling behaviour
  from a general one. This is the narrowest model coverage of any source in this base.
- **SCOPE GAP — NOT CTI.** JavaScript SAST-style security review of small Express
  applications is not threat intelligence. Admitted under the same standard as src-0008,
  src-0013 and src-0014, with the gap recorded. Note it is also the same broad task
  family as src-0008 (JavaScript code analysis), so these two do not independently cover
  distinct domains.
- **Small benchmark.** 10 fixture projects, 44 reference findings, explicitly described
  as small applications and single-file snippets. The paper's own scale disclosure is the
  main caution against generalising.
- **Not peer reviewed, no preprint or DOI.** A company blog post. Numbers are as
  published; there is no independent re-analysis and no released per-run data located at
  access time.
- **The comparison to src-0001's CI widths is qualitative only.** "How many of 5
  repetitions contained finding X" and "bootstrapped CI width over 10 re-prompts" are not
  the same statistic and cannot be converted into one another. The two sources agree in
  *direction* (identical queries give non-identical answers; grounded/mechanical outputs
  are more stable than open-ended ones) and that is the extent of the claim this source
  supports jointly with src-0001.
- Retrieved by a single automated fetch of the blog URL on 2026-07-29. Quotes above were
  returned verbatim; no table was present to pull, and the per-configuration breakdown
  (which of the six configurations produced which unmatched findings) was NOT captured
  and should be pulled by a future cycle if anyone wants a per-model stability figure.

### What the recovered tables add, and what must travel with them

1. **The "grounded stable / volunteered unstable" split is not uniform across models — it
   is roughly an order of magnitude wide.** Unique unmatched findings run 5 (Opus 4.6
   Medium) to 60 (Sonnet 4.6 Medium), a 12x spread on identical inputs, and the
   fully-stable share of unmatched findings runs 60.0% down to 8.3%. The aggregate figures
   in key_claim 1 average over configurations that differ enormously. Any use of the
   84.8% / 13.7% aggregates should say so.
2. **The baseline row is definitionally 100%, not an empirical result.** Snyk Code SAST
   scores 100.0% F1 / 100.0% recall / 100.0% precision against a reference set that is
   *defined as Snyk Code's own findings* ("44 Snyk Code reference findings"). This is a
   tautology, not a measurement, and it is the vendor-self-interest limitation above made
   concrete. **Do not cite the baseline row as evidence that SAST outperforms LLMs.**
3. **Precision and recall move in opposite directions across the model families** —
   Opus configurations 89.8-91.5% precision at 68.0-68.2% recall, Sonnet configurations
   58.6-62.6% precision at 80.9-81.3% recall. A precision-only or recall-only report of
   this benchmark would have ranked the families oppositely. Recorded here because it is a
   live worked example of the metric confound in `ctr-0001`, though on a different task.
4. **Still absent:** no per-run data, no confidence intervals, no non-Anthropic model, and
   no statement of how the 44 reference findings were validated beyond being Snyk Code
   output. The source's existing limitations all stand unchanged.

No contradiction entry is opened. Nothing here conflicts with a supported claim elsewhere
in the base; the substance of both stored key_claims is confirmed, and the defects are in
